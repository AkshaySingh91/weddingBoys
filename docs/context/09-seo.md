# 09 — SEO: Current State and Outstanding Gaps

**Read this document before doing any SEO work.** The entire migration from
React/Vite to Next.js was undertaken to win organic Google traffic and convert
it into real clients.

An SEO audit was carried out on 5 September 2026 and the highest-priority
findings were fixed the same day. This document records **what is in place** and
**what still remains**.

---

## Part 1 — What is in place

### Real server-rendered HTML
The old Vite SPA served one near-empty HTML shell for every URL. Google now
receives fully-rendered HTML across the public site.

### Incremental Static Regeneration
| Route | Revalidate |
|---|---|
| `/` | 60s |
| `/blogs`, `/blogs/[slug]`, `/[slug]` | 1 hour |
| `/sitemap.xml` | 1 hour |

### `robots.txt` — `app/robots.js`
Generated by Next's file convention. Allows the site, disallows `/admin` and
`/search-result`, declares the canonical `Host`, and points at the sitemap.

### `sitemap.xml` — `app/sitemap.js`
Generated hourly, so new posts and films appear without a deploy. It covers:

- the 10 static public routes, with per-route `changeFrequency` and `priority`
- every published **blog post** (`/api/blogs`)
- every **film** detail page (`/api/videos`)
- every **photo** detail page (`/api/photos`)
- any **CMS-built page** under `/[slug]` (`/api/content`)

Every fetch fails soft: if the API is unreachable the sitemap still builds with
whatever it could retrieve, rather than breaking the build.

### One canonical host — `lib/siteConfig.js`
`SITE_URL` is the single source of truth, defaulting to the bare domain
`https://theweddingboys.in` and overridable with `NEXT_PUBLIC_SITE_URL`.
Previously the root layout declared the bare domain while `lib/blogApi.js`
declared the `www` host, so blog canonicals pointed at a different origin from
the rest of the site and split ranking signals. `blogApi.js` now re-exports the
shared constant.

> **Operational requirement:** the web server must 301-redirect the non-canonical
> host (and `http`) to `https://theweddingboys.in`. The application can only
> *declare* the canonical host; only the server can enforce it.

### Per-page metadata on every public route
Nine pages previously inherited the homepage title and description because they
were client components, which cannot export `metadata`. Each now has a thin
**server** `page.jsx` exporting real metadata (title, description, canonical,
OpenGraph) that renders the interactive part from `_components/*Client.jsx`:

| Route | Client component |
|---|---|
| `/films` | `films/_components/FilmsClient.jsx` |
| `/allfilms` | `allfilms/_components/AllFilmsClient.jsx` |
| `/photos` | `photos/_components/PhotosClient.jsx` |
| `/team` | `team/_components/TeamClient.jsx` |
| `/about-us` | `about-us/_components/AboutClient.jsx` |
| `/contact` | `contact/_components/ContactClient.jsx` |
| `/varanasi` | `varanasi/_components/VaranasiClient.jsx` |

`/dharaa-event-management` and `/search-result` were already server components
and simply gained `metadata`. All ten public pages now have **unique** titles
and descriptions.

`/search-result` is additionally `robots: { index: false, follow: true }` —
search-result pages are thin, parameterised, near-duplicate content.

### No duplicate URLs from the CMS catch-all
The `/[slug]` catch-all previously served `/home` and `/about` as second copies
of `/` and `/about-us`, because CMS pageKeys like `home` and `about` exist to
feed content blocks to hand-built routes rather than to create standalone URLs.
`RESERVED_CMS_PAGE_KEYS` in `lib/siteConfig.js` is now honoured by both the
catch-all (which 404s on those keys) and the sitemap (which omits them).

### Honest structured data
The root layout emits `Organization` and `WebSite` (linked by `@id`) plus
`VideoProductionService`.

A `VideoObject` was **removed**. It described a "Cinematic Wedding Highlight
Film" whose `thumbnailUrl` (`/video-thumb.jpg`), `contentUrl`
(`/videos/highlight.mp4`) and `embedUrl` (`/embed/highlight`) did not exist,
with a placeholder `uploadDate` — and it was emitted on every page, including
pages with no video. Structured data that does not describe real, present
content violates Google's structured-data policies and risks a manual action.
A `VideoObject` belongs on individual film pages, built from that film's real
asset.

### Complete internal linking
Every public page is reachable from the global chrome. `/blogs` and `/varanasi`
were added to the navbar; the footer gained an "Explore" block linking all ten
public routes, including `/allfilms` and `/dharaa-event-management`. Previously
`/blogs` — the main organic-search surface — was linked from nowhere at all.

### Per-post SEO on the blog
`/blogs/[slug]` implements `generateMetadata` producing per-post title,
description, canonical and OpenGraph tags, backed by `metaTitle`,
`metaDescription`, `canonicalUrl`, `socialTitle`, `socialDescription`,
`keywords` and `seoScore` on the model, with live character counters in the
editor against the 60/160-character targets.

### Image optimisation and fonts
`next/image` with Cloudflare Image Resizing (`format=auto` → AVIF/WebP, exact
layout widths, blur placeholders, no upscaling), and `next/font` with CSS
variables. See [08 — Media pipeline](./08-media-pipeline.md).

## Part 2 — What still remains

### 1. No `BlogPosting` / `BreadcrumbList` structured data — **medium**
Blog posts have strong `<meta>` coverage but no per-post JSON-LD. A
`BlogPosting` (headline, image, `datePublished`, `dateModified`, `author`,
`publisher` — the publisher can reference the existing
`${SITE_URL}/#organization` node) plus `BreadcrumbList` is what earns rich
results for article content.

`LocalBusiness` markup is also worth adding: the studio serves specific Indian
cities and local intent is a large share of wedding-vendor search.

### 2. Film and photo detail pages have no per-page metadata — **medium**
`/films/[videoId]` and `/photos/[photoId]` are in the sitemap but export no
`generateMetadata`, so they inherit the site-wide title. Every wedding film is a
potential landing page for a query like *"wedding cinematography Varanasi"*.

Add `generateMetadata` built from the couple's names, location and shoot date,
and add a **real** per-film `VideoObject` — this is where the structured data
removed from the global layout properly belongs.

### 3. `<img>` instead of `next/image` on public pages — **medium**
`team/_components/TeamClient.jsx`, `photos/[photoId]/page.jsx` and the
search-result components use plain `<img>`, bypassing the CDN resizing pipeline.
Image weight is a Core Web Vitals input and therefore a ranking factor. ESLint
already flags each one as a warning.

### 4. Missing `alt` text — **low**
Several images have empty `alt`. The `Media` model already has an `altText`
field; the admin should require it on upload.

### 5. Leftover CORS origin — **low**
The backend still allows `http://localhost:5173`, the dev port of the deleted
Vite app.

## Verification

After the fixes, on a production build served locally:

- `/robots.txt` and `/sitemap.xml` both resolve; the sitemap contained 41 URLs
  (10 static + blog + film + photo detail pages).
- All 10 public pages return **10 unique `<title>` values** — previously 8 of
  them shared the homepage title.
- Canonicals resolve to the bare domain on every page, blog posts included.
- `/search-result` returns `<meta name="robots" content="noindex, follow">`.
- `/home` and `/about` now return **404** instead of duplicating `/` and
  `/about-us`.
- The homepage HTML links to all ten public routes.
- No reference to `video-thumb.jpg`, `highlight.mp4` or `/embed/highlight`
  remains in any rendered page.
