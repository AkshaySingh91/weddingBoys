# 06 — Authentication & Security

The auth system was rebuilt during the Next.js migration. The old
`session-token` cookie and its fallback path have been **removed entirely** —
pre-migration cookies are no longer honoured anywhere.

## Token model

Two JWTs, both delivered as **signed, HttpOnly cookies**. Neither is ever
readable from JavaScript.

| Token | Cookie (prod / dev) | Lifetime | Purpose |
|---|---|---|---|
| Access | `__Secure-admin-token` / `admin-token` | 15 minutes | Sent with every authenticated request |
| Refresh | `__Secure-admin-refresh` / `admin-refresh` | 30 days | Exchanged for a new access token; matched against a `Session` document |

Defined in `Backend/constants.js` alongside the shared `baseCookieOptions()`:
`httpOnly`, `secure` in production, `sameSite: 'lax'`, `path: '/'`, `signed`,
and `domain: '.theweddingboys.in'` in production.

### Why `__Secure-` and not `__Host-`

`__Host-` forbids the `Domain` attribute, which would scope the cookie to the
single host that set it (the API). But the Next.js edge proxy runs on
`admin.theweddingboys.in` and must be able to *read* the cookie to gate routes,
so it has to be domain-scoped to `.theweddingboys.in`. `__Host-` is therefore
architecturally incompatible here; `__Secure-` gives the prefix protection that
is compatible. This is a deliberate, documented trade-off — don't "fix" it.

The prefix is dropped outside production because local development runs over
plain HTTP, where the browser would reject a `__Secure-` cookie.

## Login flow

```
POST /api/admin/auth/login
        │
        ├── MFA disabled ──► access + refresh cookies set ──► /admin/dashboard
        │
        └── MFA enabled ───► short-lived MFA temp token (5 min)
                                  │
                                  ├── POST …/mfa/login-verify      (TOTP code)
                                  └── POST …/mfa/recovery-verify   (recovery code)
                                              │
                                              └──► cookies set
```

**Brute-force mitigation:** 5 failed logins locks the account for 15 minutes
(`MAX_FAILED_LOGINS`, `ACCOUNT_LOCK_MS`).

## Silent refresh

`Next-Frontend/lib/apiClient.js` is the client-side backbone. `apiFetch`:

1. Always sends `credentials: 'include'`.
2. On a `401`, calls `POST /api/admin/auth/refresh` **once** and retries the
   original request.
3. Coalesces concurrent refreshes through a module-level `refreshInFlight`
   promise, so a burst of simultaneous 401s triggers exactly one refresh.

Use `apiFetch` / `apiJson` for all new authenticated client code. Several older
admin screens still call bare `fetch` — those work, but do not get the retry.

## Multi-factor authentication

TOTP via `otplib`, with a QR code generated by `qrcode` and rendered at
`/admin/security`. Recovery codes are generated by `Utils/recoveryCodes.js`,
shown once in `RecoveryCodesModal`, and stored hashed.

Endpoints: `mfa/setup` → `mfa/verify-setup` → (`mfa/disable`,
`mfa/regenerate-codes`).

## Sessions

Every login creates a `Session` document holding the **hashed** refresh token
plus device fingerprint (User-Agent), IP and `lastUsedAt`. A user can list their
own sessions (`GET /api/admin/auth/sessions`); a SuperAdmin can revoke another
user's (`DELETE /api/admin/users/:id/sessions`). Revocation flips `isValid`, so
the next refresh attempt fails and the session dies within 15 minutes at worst.

## Invite-only onboarding

There is **no public signup**. The old React app had a 532-line `Signup.jsx`
gated behind a shared studio invite code; it was deliberately not migrated.

```
SuperAdmin → POST /api/admin/users/invite (email + role)
                → InviteToken (hashed, expiring, single-use) + email
                → /admin/accept-invite/[token]
                → POST /api/admin/users/accept-invite  → Admin created
```

`PUBLIC_ADMIN_PATHS` in `proxy.js` deliberately notes this: *"Self-service
signup is gone — onboarding is invite-only."* If you reintroduce a signup route
you must also add it there, and you should expect to be asked why.

## Authorisation (RBAC)

`Backend/Middleware/rbac.js`:

```js
router.put('/x', verifyToken, requireRole([ROLES.SUPER_ADMIN]), handler)
```

- `requireRole(roles)` — 401 with no role, 403 if not allowed.
- **SuperAdmin implicitly passes every check**, so it never needs to be listed.
- `requireSuperAdmin` is the shorthand.

Enforcement is server-side and per-endpoint. The admin UI does not hide screens
by role, so **never rely on the frontend for authorisation** — always add the
guard to the route.

## The edge gate is UX, not security

`proxy.js` checks only that an auth cookie is *present*; it does not verify the
JWT. It exists to avoid rendering an admin shell to signed-out visitors. Real
verification happens in `verifyToken` on every API call. Do not move an
authorisation decision into the proxy.

### Signing in locally on `admin.localhost:3000`

In production the cookie is scoped to `.theweddingboys.in`, so both the API and
`admin.theweddingboys.in` see it and the edge gate works.

Locally there is no equivalent scope. The API on `localhost:8080` sets a
**host-only** cookie for `localhost`, which the browser never sends to
`admin.localhost`. The gate therefore saw no session and redirected every admin
navigation back to `/admin/login` — sign-in looked like it silently did nothing,
even though the password, the TOTP code and the `Set-Cookie` were all fine.

`Domain=localhost` is not a dependable fix: it is a single-label domain, clients
disagree about sharing it with subdomains, and one that refuses to *store* it
would break login entirely. So the cookie scoping is left alone and `proxy.js`
skips its gate on any `*.localhost` host instead:

```js
const isLocalDevHost = (host = '') =>
    host.split(':')[0].toLowerCase().endsWith('.localhost');

if (!isPublic && !hasSession && !isLocalDevHost(host)) { /* redirect */ }
```

This is safe because the gate is a UX affordance, not a security boundary.
`AdminAuthProvider` still calls `/api/admin/auth/me` — against the API host,
where the cookie **is** in scope whichever frontend host is used — and redirects
to the login screen itself when there is no session. Production hosts never
match `isLocalDevHost`, so the gate is unchanged there.

If you would rather have dev mirror production's subdomain scoping, set
`COOKIE_DOMAIN` (see `cookieDomain()` in `Backend/constants.js`) — for example
to a real dev domain such as `.lvh.me` — rather than removing the dev bypass.

## Other measures

- **CORS** is a pinned allowlist, with `credentials: true`.
- **Passwords** are bcrypt-hashed.
- **Password reset** uses hashed, expiring tokens delivered by email
  (`Utils/mailer.js`, nodemailer).
- **`cookie-parser`** is configured with `COOKIE_SECRET_KEY`, so cookies are
  signed and tampering is detected.

## Things to be careful about

1. Never log or return `mfaSecret`, `mfaRecoveryCodes`, `refreshTokenHash` or
   `tokenHash`.
2. Never widen CORS to `*` — credentialed requests require an explicit origin.
3. Keep `localhost:5173` in mind when tidying CORS: it is a leftover from the
   deleted Vite app and can now be removed.
4. New protected route → `verifyToken` first, then a role guard if the action is
   destructive or administrative.
